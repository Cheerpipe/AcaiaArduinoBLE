# Frequently Asked Questions (FAQ)

Automatic behaviors, safety limits, and common questions about using the **Micra Shot Stopper**. Default values correspond to a freshly flashed firmware or after a **factory reset**.

For complete technical details, see the [main README](../README.md).

## Comportamiento del shot y la balanza

| Pregunta | Respuesta |
| --- | --- |
| **No puedo hacer shots de más de 60 s. ¿Por qué?** | Existe un **límite duro de 60 s** en el firmware: ninguna ruta que cierre CN9 puede superar ese tiempo, aunque configures un valor mayor en la Web UI. Es una defensa de seguridad independiente del límite operativo (*Max BBW time*). |
| **Mi shot no dura más de ~50 s (u otro valor &lt; 60 s).** | Revisa **Configuration → Max BBW time (s)** en la Web UI. Ese parámetro define el tiempo máximo del ciclo BBW (rango 5–60 s; **por defecto 50 s**). Si lo tienes en 50 s, el shot se cortará ahí aunque el peso objetivo no se haya alcanzado. También puede influir el **A→M time guard** si la balanza se desconecta durante un shot automático (ver abajo), y el **Slow extraction guard** (por defecto **44 s**): ese máximo es un punto de decisión más corto, no sustituye el Max BBW time. |
| **A veces mi shot termina antes o después del peso objetivo y la balanza no se detiene el flujo.** | Puede deberse al **Auto-to-manual time guard** (*A→M time guard*), activado **por defecto**. Si pierdes la balanza durante un shot automático (BLE caído o stream obsoleto), el firmware **sigue intentando reconectar** durante todo el ciclo. Mientras el control por peso esté suspendido, el guard puede **cerrar CN9** en un plazo fijo desde el inicio del ciclo (modo **Auto** = tendencia de los últimos 5 shots buenos, por defecto ~30 s; modo **Manual** = límite configurado, default 30 s). Si la balanza vuelve a tiempo, el countdown A→M se apaga y vuelven BBW / Fast extraction guard. Revisa **Status** (**A→M time guard** actual): `Off` / `Idle` / `Armed` / `A→M · …s` cuando está enforced. **Shot** conserva el valor del último ciclo. |
| **A veces el shot termina con 2–4 g de más respecto al objetivo.** | Si el **Fast extraction guard** está activo (**activado por defecto**), es el comportamiento esperado cuando el peso objetivo se alcanza **demasiado pronto** (antes del tiempo mínimo de extracción). El shot entra en modo *extended* y puede seguir hasta el **peso máximo de recuperación** (p. ej. 42,5 g con objetivo 36 g) o hasta cumplir el **tiempo mínimo de brew** (p. ej. 28 s). Con buzzer compilado y Output channel en **Buzzer only** o **Scale priority**, pulsos cortos en el buzzer local marcan esa extensión (**Alerts → Extended shot pulse**: Disabled / Slow / Medium / Fast / Rapid; default **Fast**; no está en el guard). Puedes desactivar el guard en Configuration. |
| **A veces el shot termina por debajo del objetivo (p. ej. 34 g) cuando va lento.** | Si el **Slow extraction guard** está activo (**activado por defecto**), es el comportamiento esperado cuando a **44 s** (max brew time) **aún no** se ha llegado al objetivo BBW. BBW gana por peso: si llegas a 36 g a tiempo, el corte es `normal_target`. Si a 44 s ya estás sobre el piso (34 g Double / Single), corta (`slow_max_time`) y el Max BBW time (50 s por defecto) casi no se usa. Si estás bajo el piso, el shot entra en *extended* y puede seguir hasta el **min recovery** (`slow_min_weight`) **o** hasta el Max BBW time / hard 60 s, que siguen siendo el tope duro. Los mismos pulsos de **Extended shot pulse** marcan esa extensión. El max time del guard **no sustituye** el Max BBW time. |
| **El shot llega al peso objetivo pero no se detiene.** | Durante los primeros segundos aplica la **protección BBW / pre-arm** (*BBW protection*): ventana contra paradas accidentales (toque del vaso, tara lenta, ruido de peso). **Por defecto 12 s.** Hasta que termina esa ventana, el stop automático por peso está inhibido. Las primeras gotas pitan y se registran de forma independiente (no cierran la protección ni esperan al retare). Corre en paralelo al retare desde el paddle ON. |
| **¿Puedo poner el vaso después de iniciar el shot?** | **Sí**, si **Automatic retare** está activado (por defecto **Sí**) y **Require cup to start** está desactivado (por defecto **No**; si lo activas, hace falta vaso en la balanza *antes* del paddle). Durante la **ventana de retarificación** (por defecto **4 s** tras el inicio) el firmware detecta una carga estable (vaso ≥ peso mínimo de vaso, p. ej. 10 g) y envía una segunda tara **sin reiniciar** el cronómetro del shot. El vaso puede llegar en cualquier momento de esa ventana, incluidos ~2–4 s. Tras la tara hay una **gracia post-tara** (**Post-tare grace**, por defecto **2 s**; **Settings → Machine and scale → Tare**) para que la balanza vuelva a ~0 g antes de usar el peso. Después, las primeras gotas pitan y se registran; el flow medio del historial usa ese first drop. |
| **¿Por qué el shot no para exactamente en el peso objetivo?** | El firmware usa un **offset de parada aprendido** (por defecto 1,5 g, máx. 5 g) para compensar el goteo post-corte, y un corte por peso que se adelanta con las muestras recientes. En el historial verás `cut_type` y `stop_detail` (`normal_target`, `extended_max_weight`, `extended_min_time`, `slow_max_time`, `slow_min_weight`, …), no un tipo “prediction”. |
| **La balanza se desconectó a mitad del shot. ¿Qué pasa?** | En shots automáticos el control por peso se **suspende** y el firmware **sigue intentando reconectar** durante todo el ciclo (no hay lockout permanente a manual tras N segundos). Si recupera tres muestras coherentes, vuelve el stop por peso (incluido Fast extraction guard si aplica) y el **A→M time guard** deja de enforcearse. Mientras la balanza esté caída y el A→M guard esté **ON**, corre un **deadline absoluto desde el inicio del ciclo** (tendencia Auto o límite Manual) y puede **cerrar CN9** antes del límite CN9 — incluso mientras BLE sigue reintentando. En el panel verás la línea **A→M time guard** con `A→M · …s`. Si el guard está **OFF** y la balanza no vuelve, el shot sigue hasta paddle OFF o el wall CN9 / hard 60 s. |
| **Apagué “Brew by weight”. ¿Por qué no para por peso?** | Con **Brew by weight** en OFF se mantiene tara/cronómetro pero se **desactivan** el stop por peso, la retarificación automática, la protección BBW y el aprendizaje de offset. El corte depende del paddle, del límite CN9 o de **Stop** remoto. En **Home → Quick Settings**, **No-scale BBW**, **Fast extraction guard**, **Slow extraction guard** y **A→M time guard** quedan en solo lectura (siguen mostrando ON/OFF) porque solo aplican con BBW. |
| **Con BBW ON y la balanza apagada, un paddle largo no extrae (triple beep y CN9 abierto).** | Es el **guard anti-extracción BBW sin balanza** (*Avoid BBW shot without scale*, **ON por defecto**). Un paddle ON **más largo que el gesto de rinse** consume Armed y **no cierra CN9**. El siguiente paddle sí inicia un shot manual. Un gesto de rinse (ON→OFF dentro de la ventana) **sí lava**, cierra CN9 y también consume Armed → Idle (el rinse web hace lo mismo). El **triple beep** (*Manual without scale*) suena al cerrar el paddle si BBW está ON y no hay balanza — Armed o Idle, brew o rinse — sin esperar a clasificar el gesto. Con el latch Idle, brew y rinse son los de siempre (el rinse Idle no rearma). Vuelve a Armed al boot, cuando la balanza está disponible, o tras **Last shot cooldown** (default 60 min) desde el bloqueo, un rinse Armed, o el último shot terminado (no rinse). Con BBW OFF no aplica. |

## Configuración, red y acceso

| Pregunta | Respuesta |
| --- | --- |
| **¿Cuáles son las credenciales por defecto?** | Red AP: **`MicraShotStopperAP`** / contraseña WPA2 **`Micra1234`**. Web UI en AP: **`http://192.168.4.1`**, sin login. Tras **factory reset** todo vuelve a estos valores. Detalle: [Factory credentials](../README.md#factory-credentials-first-use). |
| **No encuentro la red del dispositivo tras el primer arranque.** | Sin Wi‑Fi de casa guardado, el firmware levanta el AP **`MicraShotStopperAP`** y lo mantiene (no hay apagado por inactividad de 3 minutos). Con credenciales guardadas, primero intenta STA; el SoftAP solo aparece si no asocia en ~15 s (arranque), y entonces reintenta STA en modo AP+STA. Al conectar STA, el SoftAP se apaga y la Web UI queda en la IP STA. Si se pierde el enlace **después** de haber conectado, solo se reintenta STA (no vuelve SoftAP solo); para SoftAP usa USB `AP_START` o reinicia. Para guardar Wi‑Fi STA hace falta iniciar sesión (contraseña por defecto **`Micra1234`**) y tener el paddle en OFF sin ciclo activo. |
| **¿Cómo accedo cuando ya guardé mi Wi‑Fi de casa?** | Con STA asociado, abre **`http://&lt;ip-del-dispositivo&gt;`**. La IP aparece en los logs serie (**115200** baud, con debug serie activado), en la lista DHCP del router, o es la IP fija que configuraste. La contraseña Web es la que configuraste (o **`Micra1234`** si no la cambiaste). Si una IP fija nueva no es alcanzable, en ~3 min se restaura la config anterior y se reintenta STA; SoftAP automático solo si en ese boot **aún no** hubo un join STA exitoso — si ya hubo, usa USB `AP_START` o un reset. Si el Wi‑Fi de casa cae tras haber estado online, el dispositivo **solo reintenta STA** (sin SoftAP automático); recupera SoftAP con USB `AP_START` o un reset. |
| **¿Puedo cambiar la contraseña?** | Sí. En la Web UI (**Admin → AP password**) hay que introducir la contraseña actual y la nueva. Por **USB serial**, `SET_AP_PASSWORD` fija la nueva sin pedir la actual; `RESET_AP_PASSWORD` vuelve a `Micra1234`. Cambia únicamente la contraseña WPA2 del AP. Comandos: [USB serial CLI](SERIAL_CLI.md). |
| **Perdí el Wi‑Fi o la contraseña de la UI. ¿Cómo recupero el acceso por USB?** | Conecta por USB a **115200** baud y envía comandos serie. `HELLO` debe responder `how are you` (el CLI responde aunque el debug serie esté apagado). `RESET_AP_PASSWORD` vuelve a **`Micra1234`**. `CLEAR_WIFI` olvida la red de casa. `FACTORY_RESET` borra todo. Los comandos destructivos piden paddle OFF. Catálogo: [USB serial CLI](SERIAL_CLI.md). |
| **No tengo acceso por Web UI, Wi‑Fi, BLE ni USB. ¿Cómo recupero el equipo?** | Usa la [recuperación de emergencia con el paddle](EMERGENCY_RECOVERY.md). Al energizar con paddle ON se abre una ventana local de 60 s con CN9 bloqueado abierto: tres ciclos restauran Wi‑Fi/AP/contraseña y cinco hacen factory reset. |
| **¿Puedo controlar el shot desde el móvil?** | La Web UI permite monitorización siempre. **Paddle virtual**, rinse remoto y ciclos nuevos por red requieren compilar con **`SHOT_STOPPER_ENABLE_REMOTE_CN9=1`** (desactivado en builds conservadores). **Stop** remoto abre CN9 en cualquier build autenticado. El **paddle físico siempre tiene prioridad**. |
| **La Web UI se ve como basura en `curl`.** | El HTML se sirve **gzip**. Los navegadores lo descomprimen solos. Desde terminal usa `curl --compressed http://<ip>/`. |

## Hardware y compatibilidad

| Pregunta | Respuesta |
| --- | --- |
| **¿Qué placas puedo usar?** | Solo **ESP32-S3 con PSRAM**: **N8R4** (`n8r4`, 8 MB flash + 4 MB QSPI PSRAM) o **N16R8** (`n16r8`, 16 MB flash + 8 MB OPI PSRAM, **por defecto**). Pines por defecto: paddle GPIO 21, relé GPIO 38. Particiones OTA normales: **`app3M_fat9M_16MB`** en N16R8 y **`default_8MB`** en N8R4 (slot de app ~3 MB). El ESP32 clásico y Nano ESP32 **no están soportados**. Detalle en [README → Hardware](../README.md#hardware). |
| **¿Qué balanzas son compatibles?** | El firmware se **pensó principalmente para Bookoo** (Themis Mini/Ultra): defaults, tara combinada y volumen. Vía la librería **AcaiaArduinoBLE** también: **Acaia** (Lunar, Pearl S, Pyxis…), **Felicita** (Arc) y otras. Rendimiento BLE varía por modelo/firmware. Tabla detallada: [Scale Compatibility](../libraries/AcaiaArduinoBLE/README.md#scale-compatibility). |
| **¿Cómo elijo entre varias balanzas?** | En **Settings → Machine and scale**: **Always use this scale** (ON por defecto) conecta solo la **Preferred scale**. El dropdown lista hasta 8 balanzas vistas por BLE; las no preferidas se guardan en el historial sin conectar. OFF usa la primera compatible. **Clear preferred** quita el lock (pausa 30 s) y conserva el historial. |
| **¿Funciona en máquinas distintas a la Micra?** | Este firmware está **diseñado para La Marzocco Linea Micra** (paddle en GPIO, CN9 vía relé aislado). Otras máquinas **no están soportadas oficialmente** aquí; adaptarlas exige **circuito y cableado ad hoc** (relé aislado, lectura del interruptor/paddle, alimentación). La librería original documenta otras máquinas (GS3, Mini, Silvia Pro, etc.) en un [concepto distinto](../libraries/AcaiaArduinoBLE/README.md#espresso-machine-compatibility). |
| **¿Necesito la PCB ShotStopper?** | No es obligatoria: puedes montar ESP32-S3 (N8R4 o N16R8) + relé siguiendo el README. La PCB simplifica el cableado. |
| **¿Cómo funciona el LED azul de la placa?** | GPIO 1 en HIGH mientras hay conexión BLE con la balanza (default ON). Se apaga desde **Settings → Alerts → Blue LED while scale connected**. El pin se sobreescribe al compilar con `-DSHOT_STOPPER_SCALE_CONNECTED_LED_GPIO`. Ver [README → Scale-connected LED](../README.md#scale-connected-led). |
| **En mi circuito uso GPIO distintos a los del firmware. ¿Cómo los cambio?** | Los pines **no se configuran desde la Web UI** — es una medida de seguridad para evitar asignaciones incorrectas que podrían dejar CN9 cerrado, leer mal el paddle o controlar la máquina de forma peligrosa. Hay que **editar el firmware y recompilar**. Todo vive en **`shotStopper/shotStopper.ino`**, sección *Board hardware*. **Paddle y relé** (`PADDLE_GPIO`, `RELAY_GPIO`): constantes `constexpr` del mapa ESP32-S3 (`ARDUINO_ESP32S3_DEV`: GPIO 21 / 38). Si tu placa usa otros pines, modifica ese bloque. **LED de conexión de balanza**: `SHOT_STOPPER_SCALE_CONNECTED_LED_GPIO` (default GPIO 1, active HIGH). **Seguridad externa K2** (opcional, ambos o ninguno): `SHOT_STOPPER_SAFETY_HEARTBEAT_GPIO`, `SHOT_STOPPER_CN9_FEEDBACK_GPIO`, `SHOT_STOPPER_CN9_FEEDBACK_CLOSED_LEVEL`. **Polaridad** (solo si tu hardware difiere del Micra): `PADDLE_ACTIVE_LEVEL`, `RELAY_CLOSED_LEVEL`, `RELAY_OPEN_LEVEL` — el diseño Micra asume paddle activo **LOW** y relé cerrado **LOW**. El compilador valida con `static_assert` que no haya pines duplicados ni GPIO inválidos. Se asume que quien monta su propia placa conoce su esquema, ajusta el fuente y compila según el [README → Compile](../README.md#compile). Ejemplo solo para el LED: `compiler.cpp.extra_flags=-DSHOT_STOPPER_SCALE_CONNECTED_LED_GPIO=1`. |
| **¿Por qué suenan pitidos después de que el shot terminó?** | Con **Paddle-off reminder** (por defecto activo), la balanza repite pitidos mientras el **paddle físico sigue ON** y CN9 ya está abierto — recordatorio de devolver el paddle. Intervalo por defecto **10 s**, límite **15 min**. |

## Seguridad y diagnóstico

| Pregunta | Respuesta |
| --- | --- |
| **¿Qué ocurre después de un panic o watchdog reset?** | El reinicio fuerza CN9 a **OPEN** antes de inicializar el firmware y luego arranca normalmente: no bloquea CN9 ni la Web UI y no exige una maniobra local de recuperación. Los fallos activos de hardware, feedback, timers o watchdog sí mantienen su `LOCKOUT` independiente. |
| **¿Cómo sé por qué terminó un shot?** | En el **historial de shots**: `cut_type` (`auto`, `manual`, `limit`) y `stop_detail` (`normal_target`, `extended_max_weight`, `extended_min_time`, `slow_max_time`, `slow_min_weight`, `auto_to_manual`, etc.). El panel de diagnóstico y `GET /api/v1/log` amplían detalle. |
| **El LED de la placa no se enciende con la balanza conectada.** | Comprueba **Settings → Alerts → Blue LED while scale connected** (ON por defecto) y que el enlace BLE figure como conectado. GPIO 1 HIGH = conectada; LOW = desconectada o setting off. El comportamiento de CN9 lo gobierna la máquina de estados, no el LED. |
| **¿Es seguro confiar solo en el relé del ESP32?** | **No** como garantía física absoluta. El firmware incluye watchdogs, cierre transaccional y tope de 60 s, pero un relé soldado o un GPIO corto requieren **barrera K2 externa** opcional (heartbeat + feedback aislado). Ver [Watchdog and CN9 safety](../README.md#watchdog-and-cn9-safety). |
| **Tras actualizar el core ESP32 veo `ble=fail` / balanza no detectada, pero la Web UI sí.** | En Arduino-ESP32 **3.3.6+** el core libera la RAM del controlador BLE al boot si nadie la declara. ArduinoBLE no incluye `esp32-hal-alloc-ble-mem.h`; este árbol sí (pin **3.3.11**). Si falta el include, `BLE.begin()` falla (~1 s HCI reset) y la Web UI puede seguir viva. Con ESP32-S3 + PSRAM la UI y el **host** ArduinoBLE (GAP/ATT) pueden vivir en SPIRAM; el **controlador** BLE sigue en SRAM interna: valida M72/M73 y mira `HEALTH` `bleHostAllocPsram`. |

## Dónde ajustar cada comportamiento

| Comportamiento | Ajuste en Web UI (Configuration) |
| --- | --- |
| Límite de tiempo del shot (≤ 60 s) | **Max BBW time (s)** |
| Parada temprana/tardía por pérdida de balanza | **A→M time guard** (Enable, Limit mode, Manual limit, Trend, Reset samples). También **Home → Quick Settings** (ON/OFF; solo lectura si BBW está OFF) |
| Shot que pasa del objetivo unos gramos | **Fast extraction guard** (Enable, Min brew time, Max recovery). Pulsos: **Alerts → Extended shot pulse** (Disabled / Slow / Medium / Fast / Rapid). También **Home → Quick Settings** (ON/OFF; solo lectura si BBW está OFF) |
| Shot lento que cierra bajo el objetivo | **Slow extraction guard** (Enable, Max brew time, Min recovery). Mismos pulsos de **Extended shot pulse**. También **Home → Quick Settings** (ON/OFF; solo lectura si BBW está OFF) |
| No para al llegar al peso al inicio | **BBW protection (s)** |
| Vaso tardío | **Automatic retare**, **Retare window (s)**, **Minimum cup weight (g)** |
| Tras tara, peso de vaso o first drop incorrectos | **Post-tare grace (s)** (**Settings → Machine and scale → Tare**; default 2 s; 0.5–10 s). Inactivo si Automatic tare está off. |
| Sin stop por peso | **Brew by weight** (OFF) |
| Primer shot BBW sin balanza bloqueado | **Machine and scale → No-scale BBW** (*Avoid BBW shot without scale*, **Last shot cooldown**). También **Home → Quick Settings** (ON/OFF; solo lectura si BBW está OFF) |
